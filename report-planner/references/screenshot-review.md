# 分阶段截图验收

## 1. 目标

学生做完一段实验后，把截图发回来；你检查：

- 这张图**对应哪一步**；
- 图里**有没有这一步必须包含的信息**；
- 图里的结果**是否符合预期**；
- 如果不对，**缺什么、要重拍哪里、预期画面是什么**。

你只验收证据，不替学生做实验、不 P 图、不伪造结果。

## 2. 分阶段提交（省 token，早发现问题）

推荐节奏：

| 阶段 | 提交内容 | 验收后 |
| --- | --- | --- |
| 第 1 阶段做完 | 执行卡第 1 组 L1 证据 | 通过后进入下一组 |
| 第 2 阶段做完 | 执行卡第 2 组 L1 证据 | 通过后进入下一组 |
| 收尾 | pcap、脚本、日志、缺失的 L2/L3 证据 | 归档 |

**阶段名以执行卡为准**（可能是"准备/操作/采集/分析"），不要硬套"基础/进阶"；
有的实验只有一次操作，一次提交即可。**不要等全部做完再一次性发几十张图。**
一次只读当前阶段；已通过的图不重复读。

### 先和用户约定

- 放哪：默认放在任务目录下的 `Pictures/`；也可以直接上传。
  目录**可以由用户自定义**；用户直接丢在当前目录也行（会乱，但允许）。
  **不要假设一定有"基础/进阶"子目录**，用户自己分了就按用户的目录结构读；
- 怎么读：直接上传的图按对话读取；目录里的先列出文件清单，再按当前阶段读取，
  不要盲目全读；
- 命名：有证据 ID 最好，如 `S8_PacketIn_v1.png`；没有就请用户说明对应步骤；
- 没有文件名：请用户按步骤顺序说明，或先发一个文件清单；
- 图太大：请用户裁掉无关桌面区域，保留完整窗口和关键字段；
- 图太多：请用户按阶段打包，或只发 L1 关键图。

### 2.1 目录扫描边界

**可以扫：**

- 任务目录本身；
- 任务目录下的 `Pictures/`；
- 用户明确指定的其他目录（相对或绝对路径都行）；
- 最多向下 2 层（`Pictures/` 和它的一级子目录）。

**不要扫：**

- 父目录、盘符根目录、系统目录、桌面/下载/相册等无关目录；
- `.git`、`node_modules`、`__pycache__`、虚拟环境、缓存目录；
- 与任务无关的个人照片、聊天截图、证件照；
- 外链/云盘链接（只读本地文件）。

**不要做：**

- 不移动、不改名、不删除用户文件；
- 不把图片上传到外部服务；
- 不读与当前阶段无关的图；
- 不确定时先列清单问用户，不要"自由"到越界。

### 2.2 来源与格式

| 来源 | 处理 |
| --- | --- |
| 直接上传 | 按对话中的图片读取 |
| `Pictures/` 或用户指定目录 | 先列清单（路径/大小/修改时间），再按阶段读取 |
| 当前目录散落图片 | 只列图片扩展名，按文件名/时间筛；确认后再读 |
| `.heic` / `.webp` | 请用户导出为 PNG/JPG；或先转换再看 |
| PDF / Word 里的截图 | 请用户导出图片，或只截关键页；不要整份读 |
| zip / 压缩包 | 请用户解压到 `Pictures/`，或先列目录再决定 |
| 手机拍屏 | 允许，但要求清晰、无遮挡；优先用系统截图 |
| 云盘/外链 | 不打开；请用户下载到本地 |

### 2.3 文件清单模板（文件名乱时用）

如果用户直接把图丢在当前目录、文件名没有规律，先让用户（或你自己列）发一个清单：

| 文件 | 对应步骤/证据 ID | 说明 |
| --- | --- | --- |
| `IMG_001.png` | S6 / E6 | pingall 结果 |
| `IMG_002.png` | S8 / E8 | Packet-In 详情 |
| `IMG_003.png` | S10 / E10 | Flow-Mod 匹配域 |

没有清单时，按"修改时间 + 内容 + 用户说明"推断；仍不确定就问，不要猜。

### 2.4 重复图、旧图、非图片证据

- **同一证据多张图**：选最完整的一张；两张互补可以合并验收
  （如"接口选择"+"过滤器/报文列表"）；其余标为备份，不重复读。
- **旧图/旧环境**：看时间、版本、拓扑是否与本次一致；不一致先问用户是否本次采集。
- **同一图对应多个证据**：可以复用，但要在验收记录里写明它同时支撑哪些证据。
- **非图片证据**：数据表、日志、代码、问卷、访谈记录按同样的
  "对应步骤 / 必须包含 / 预期结果 / 可读性"四件事验。
- **截图是旧学期/别人的**：不直接采用；先问来源，按学术规范处理。

## 3. 每张图怎么验

### 3.1 先定位

1. 从文件名/用户说明找到证据 ID（如 E8）；
2. 在執行卡 §1 找到该 ID 的"必须包含"；
3. 在執行卡 §2 找到对应步骤和"达成效果"；
4. 确认用户声称的步骤与实际截图内容一致。

### 3.2 再核对四件事

| 检查项 | 问法 | 不合格示例 |
| --- | --- | --- |
| 对应步骤 | 这张图确实来自这一步吗？ | 用户说 E10 Flow-Mod，图里却是 Packet-In |
| 必须包含 | 版本/命令/字段/结果都在画面里吗？ | 只截了报文列表，没展开报文树 |
| 预期结果 | 结果与执行卡的"达成效果"一致吗？ | 只看到 `pingall` 命令，没有结果行 |
| 可读性 | 关键字段清晰、没被裁掉吗？ | 标题栏/路径/输出被裁掉；字太小 |

### 3.3 判定

| 判定 | 含义 | 处理 |
| --- | --- | --- |
| **通过** | 关键信息齐全，结果符合预期 | 标记通过，进入下一张/下一阶段 |
| **部分通过** | 关键信息在，但缺次要信息（如时间、路径、版本） | 说明缺什么，可补拍；不阻断下一阶段 |
| **不通过** | 缺关键信息、对应错步骤、结果不符 | 给出具体补拍清单，要求重拍或补做 |
| **截图合格，结果不符** | 图很清楚，但实验结果不对 | 不要求重拍同一张图；转到排错分支，先解决问题 |
| **需人工复核** | 看不清、字段含义拿不准、来源不明 | 明确说"需人工复核"，不要硬判通过/不通过；请用户补图或问老师 |

**不要用"看起来没问题"代替具体核对。** 必须说出"看到了哪个字段、值是多少"。

## 4. 不同类型截图的检查清单

### 4.1 终端/命令输出

- [ ] 命令本身可见（不是只截结果）
- [ ] 完整输出可见，关键行没有被截断
- [ ] 提示符/路径/主机名可见（证明在哪台设备上执行）
- [ ] 返回码/成功/失败标志可见
- [ ] 失败时保留完整报错上下文

**常见不合格**：只截最后一行 `success`；命令和输出分开两张图；用文字复述代替截图。

### 4.2 Wireshark / OpenFlow 报文

- [ ] 过滤器可见（`openflow_v1` / `openflow_v4` / `.type == 10` 等）
- [ ] 接口可见（`any` 或具体网卡）
- [ ] 报文列表 + 报文详情树同时可见
- [ ] 关键字段展开：Version、Type、Length、Buffer ID、In port、Reason、Match
- [ ] Packet-In 的内层报文展开（ICMP/ARP）
- [ ] 需要配对时，Packet-In 与 Flow-Mod 的 Buffer ID 同时可见
- [ ] 报文编号/时间顺序可见（供 writer 画流程图）

**常见不合格**：只截列表不展开树；Version/Type 看不到；只截其中一条，无法说明配对关系。

### 4.3 拓扑 / 网络配置

- [ ] 设备名/节点名可见
- [ ] 链路关系可见（谁连谁）
- [ ] 关键接口/IP/VLAN/状态可见
- [ ] 设备型号/版本可见
- [ ] 标注没有遮挡关键字段

**常见不合格**：只截局部节点；看不到设备名；连线被裁掉。

### 4.4 流表 / 表项

- [ ] 完整 `dump-flows` 输出
- [ ] priority、match、actions、n_packets/n_bytes 可见
- [ ] 能区分 ping 前/后两张表
- [ ] 交换机名（s1）可见
- [ ] 需要对比时，两张图的时间/顺序能对上

**常见不合格**：只截 table-miss；只截新增表项但没有前后对比；看不到 priority/actions。

### 4.5 代码 / IDE

- [ ] 文件名/路径可见
- [ ] 关键代码段完整（函数名、参数、返回值）
- [ ] 运行/编译/测试结果可见
- [ ] 代码与报告描述一致
- [ ] 没有把无关代码截进来

**常见不合格**：只截代码不截运行结果；文件名看不到；代码与报告里的参数不一致。

### 4.6 数据表 / 电子表格

- [ ] 表头、单位、样本量可见
- [ ] 原始数据与处理后数据分得清
- [ ] 关键行/列没有被截断
- [ ] 异常值/缺失值标注可见
- [ ] 图表有坐标轴、单位、图例

**常见不合格**：只截汇总值；没有单位；只截图表不截原始数据。

### 4.7 网页 / 平台数据

- [ ] URL/页面标题可见
- [ ] 日期/筛选条件可见
- [ ] 关键数据/图表可见
- [ ] 数据来源/报告名称可见
- [ ] 没有把广告/无关内容当数据

**常见不合格**：没有 URL/日期；只截结论不截来源；截了网图但说是自己调查的。

### 4.8 流程图 / 示意图

> **报告里的流程图/示意图默认由 writer 绘制，不要求用户提交。**
> 如果用户自己画了，或任务产物本身就是图（设计草图/原型），才按本节检查。
> 用户只需要留下支撑图的原始证据：报文顺序、packet number、拓扑截图、数据表、引用。

- [ ] 消息顺序/方向清楚
- [ ] 每条消息的类型/作用标注
- [ ] 触发关系/分支清楚
- [ ] 不是把步骤列表换个框
- [ ] 与截图/字段值对得上

**常见不合格**：只画"步骤 1→2→3"；没有消息方向；图里出现截图里没有的报文。

### 4.9 照片 / 现场 / 访谈

- [ ] 时间/地点/对象可见（可公开部分）
- [ ] 关键细节清楚（全景 + 细节）
- [ ] 涉及他人时已取得同意/已匿名
- [ ] 不是网图/生成图
- [ ] 与报告描述一致

**常见不合格**：只拍氛围不拍关键细节；涉及他人隐私未处理；用网图冒充现场。

## 5. 验收记录格式

建议写 `截图验收.md`：

```markdown
# <实验> 截图验收

- 验收阶段：<阶段名> / 收尾
- 验收时间：YYYY-MM-DD
- 提交文件：<文件名列表>

| 证据 ID | 文件 | 对应步骤 | 预期内容 | 结果 | 处理 |
| --- | --- | --- | --- | --- | --- |
| E6 | S6_pingall.png | S6 | 12/12、0% dropped | 通过 | — |
| E8 | S8_PacketIn_v1.png | S8 | Version 1.0、Type 10、Buffer ID、Reason | 不通过：未展开报文树 | 重新截图，展开 Packet-In 详情 |

## 阶段结论

- 已通过：E1、E2、E3、E6、E8
- 待补拍：E10（Flow-Mod 匹配域未展开）
- 可以进入下一阶段：否 / 是

## 补拍清单

1. **E10 Flow-Mod**：选中 OFPT_FLOW_MOD，展开 OpenFlow match 字段，
   必须看到 wildcards、in_port、eth_src、eth_dst、cookie。
   预期画面：左侧报文列表选中 Flow-Mod，右侧详情树展开到 match。
```

## 5.5 验收后的下一步（不要直接跳 writer）

验收结束，按结果给用户**三个选项**，不要只问“要不要进入 writer”：

| 结果 | 提示 |
| --- | --- |
| 本阶段通过，还有后续阶段 | 继续下一阶段，完成后再发截图。 |
| 本阶段通过，所有阶段完成 | A. 直接交给 writer；B. 先按实际情况修改执行卡/指导书（升 v1.1）；C. 补 L2/L3 证据。 |
| 有部分通过/不通过 | 给补拍清单；若执行卡与实际不符，先改执行卡再验收。 |
| 截图合格但结果不符 | 先排错，不重拍同样结果的图；必要时更新失败分支。 |

**只有所有阶段 L1 通过 + 步骤完成/跳过**，才建议进入 writer。
验收时顺手检查执行卡是否需要更新：步骤不符、漏字段、失败分支没覆盖，都应改卡，
不要带着错卡继续做。

## 6. 常见不合格与补拍话术

| 情况 | 话术 |
| --- | --- |
| 只截列表，没展开树 | "这张图能看到报文列表，但看不到字段。请选中这条报文，把下方详情树展开到 Version/Type/Length/Buffer ID/Reason，再截一张。" |
| 缺少命令 | "图里只有结果，没有命令。请把执行命令和输出放在同一张图里，保留提示符。" |
| 缺少版本/路径 | "看不到设备名/版本/路径。请把窗口标题栏或 `show version` 一起截进来。" |
| 对应错步骤 | "这张图是 Packet-In，不是 Flow-Mod。请重新选中 OFPT_FLOW_MOD 再截。" |
| 结果不符 | "截图本身合格，但 ping 没有 5/5，说明实验还没通过。先按 §5 排错，解决后再重截结果。" |
| 图太大/太糊 | "关键字段看不清。请只截相关窗口，放大到能看清字段，再发一次。" |
| 缺一张 | "本阶段还缺 E10（Flow-Mod 匹配域）。补这一张后，本阶段就齐了。" |

### 6.5 其他边界情况

| 情况 | 处理 |
| --- | --- |
| 手机拍屏、反光、角度歪 | 能看清就收；关键字段看不清就要求系统截图或重拍 |
| 聊天软件压缩 | 要求原图；压缩图只用于确认内容，不用于报告 |
| 标注遮挡关键字段 | 要求未标注原图，或把标注移到空白处 |
| 多显示器/窗口重叠 | 要求只截目标窗口，保留标题栏和关键字段 |
| 滚动页面只截一半 | 要求补下半部分，或截全页 |
| 终端字号太小 | 要求放大字号/窗口后重截 |
| 深色模式/低对比度 | 能看清就收；看不清要求调亮或换浅色主题 |
| 光标/提示框遮挡 | 要求移开光标/提示框再截 |
| 截图含他人姓名/学号/账号 | 要求打码后重发 |
| 截图含答案/密钥/内部地址 | 要求脱敏；报告中不要出现 |
| 旧环境/旧学期截图 | 先问是否本次采集；不是就要求重做或说明 |
| 别人发的截图 | 问清来源；个人报告不能直接用他人截图 |
| 分组任务，截图是组员做的 | 问清分工；个人报告用自己负责部分的证据；公共截图注明来源 |
| 远程/虚拟机实验 | 截图要能看出宿主机/虚拟机/远程环境；必要时补连接信息/版本 |
| 物理设备/仪表读数 | 照片含读数、单位、设备标识、时间；关键细节补特写 |
| 老师指定截图格式 | 按老师要求，优先于本清单 |
| 只有成功结果、没有命令 | 部分通过；要求补命令/上下文 |
| 只有失败结果 | 可能是排错证据，不是通过；按排错流程处理 |
| PDF/Word 里的截图 | 要求导出原图；不要整份读 |
| HEIC/WebP/大图 | 要求导出 PNG/JPG，或先转换再看 |
| 一张图对应多个证据 | 可以复用，验收记录里写清 |
| 多张图拼一个证据 | 可以合并验收，记录全部文件 |
| 想用一张"总览图"代替所有步骤 | 不通过；每个证据要有对应画面 |
| 录屏/视频/GIF | 只取关键帧；或要求关键步骤截图 |
| 老师给的示例图 | 不能当自己的实验证据 |
| 网图/生成图 | 拒绝；要求实际采集 |
| 要求 P 图/改结果 | 拒绝；只验收真实证据 |

## 7. 省 token 的规则

- **按阶段验收**：按执行卡的阶段/证据组分组，不要一次读全部。
- **只读当前阶段**：已通过的图不重复读；需要复核时再读。
- **先看文件名/清单**：让用户先发文件列表，缺什么一目了然。
- **图太大先裁**：保留完整窗口和关键字段，裁掉无关桌面。
- **一次只问一个补拍点**：把该阶段所有不通过项汇总成一张补拍清单，不要逐张来回问。
- **验收记录落文件**：后续不用重新看旧图，直接看 `截图验收.md`。

## 8. 隐私与规范

- 截图中的姓名、学号、手机号、他人账号、内部 IP/密钥要打码；
- 访谈/照片涉及他人时，先确认同意/匿名；
- 不 P 图、不伪造截图、不用网图冒充现场；
- 发现截图与报告描述不一致时，先问用户，不直接判作弊；
- 验收只判断"证据是否支撑报告结论"，不替老师打分。

## 9. 阶段门（按执行卡的阶段分组）

### 通用规则

- **每个阶段的 L1 证据全部通过，才进入下一阶段。**
- 阶段名和证据 ID 以执行卡为准；不一定是"基础/进阶"，也可能是"准备/采集/分析"。
- 下面是某网络实验的示例，其他任务按执行卡替换。

### 示例：阶段一通过条件

- [ ] E1-E3：环境/拓扑/IP
- [ ] E6：pingall 12/12
- [ ] E8/E10：Packet-In / Flow-Mod 关键字段
- [ ] E11：报文顺序/packet number 记录（供 writer 画流程图）
- [ ] 至少一份本阶段 pcap

### 示例：阶段二通过条件

- [ ] E13/E14：RemoteController / RYU
- [ ] E15：握手序列
- [ ] E16/E18：流表前后
- [ ] E17：ping 结果
- [ ] E19-E21：三类报文与 Buffer ID 配对
