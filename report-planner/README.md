# report-planner

把实验指导书、任务书、报告模板、评分表转化为一份**现场能照着做的实验执行卡**：
步骤/预期结果速查、逐步照做清单、每步截图提示、截图速查卡、失败分支、报告章节映射；
并支持分阶段截图验收（默认从 `Pictures/` 读取，也可直接上传）。

默认产出**两份**：`实验执行卡.md`（现场照着做）和 `实验指导书.md`（完整方案：
目的、原理、环境、步骤、证据、报告映射、差异）。执行卡先给实验目标、阶段目标，
再给"这一步做什么、达成什么效果、截什么图、卡住了怎么办"；背景、目的矩阵、
差异分析放在指导书里。**只出执行卡不够。**

本 Skill 可单独使用，也可由 `report-worker` 编排；不绑定学校、课程或学科，
按任务形态（操作验证、编程、测量、调研、设计策划、案例文献、项目、体验观察）适配。

它解决的是这类问题：

- 指导书只写了"做什么"，没写"先做什么、做到什么算成功"；
- 指导书/模板没说要截什么图，不知道实验过程中该留哪些证据；
- 实际实验和指导书不一样（设备不足、老师口头改方案），不知道报告怎么写；
- 调研、案例分析、商业计划书、课程项目等非实验任务，不知道该拆成哪些步骤；
- 实验做完了才发现少拍了关键截图，只能返工。

## 两份文件怎么用

| 文件 | 定位 | 用途 |
| --- | --- | --- |
| `实验执行卡.md` | **即开即用版** | 现场照着做：步骤、截图、验收、失败分支 |
| `实验指导书.md` | **完整版（必做）** | 确认实验目的、实际方案差异、证据细节、报告结构；交给 `report-writer` 当规划输入 |

> 旧名 `实验规划书.md` 也接受。它是我们整理的计划，不是老师给的课程指导书，
> 也不是报告草稿；writer 仍以实际截图和数据为准。

## 定位

```
report-planner（规划） → report-writer（写报告） → report-reviewer（审核）
```

- **planner 只做规划**：不代做实验、不编数据、不写报告正文；
- **writer 按规划写报告**：执行卡/实验指导书里的章节映射、证据 ID、差异说明可以直接交接；
  实验指导书是规划输入，不是报告草稿，writer 仍需要实际采集的截图与数据；
- **reviewer 按同一套口径审核**：用户描述优先、只审需编写区域、条件项不扣分。

## 核心方法

1. **用户描述优先**：实际方案（含老师口头方案、设备限制、替代做法）高于指导书；
   差异逐条记录，实验目的逐条核对，不擅自删减。
2. **按任务形态分类**：操作验证、编程实现、测量实验、调查调研、设计策划、
   案例文献、项目综合、体验观察——不按学科分类，文科/商科/工科都适用。
3. **截图优先，证据链兜底**：执行卡把截图提示写进每一步；截图不是唯一证据，
   数据表、日志、代码、照片、问卷、访谈、引用、版本记录同样有效。
4. **L1/L2/L3 分层**：必采、建议采、保险采；关键步骤多拍一张全景/细节，
   防止老师后续加要求导致返工。
5. **执行卡优先**：第 0 节是一张 8~12 行的"步骤 / 预期结果 / 截图"速查表，
   不是泛泛目标；后面才是详细操作。每一步写"步骤与目标"和"达成效果"，
   不是只写"做什么"。
6. **变更不重做**：方案变了先判断旧证据是否仍有效，只补缺口；版本记录不覆盖旧版。
7. **分阶段截图验收**：按执行卡的阶段分组，做完一组交一组；默认从 `Pictures/` 读取，
   也可直接上传，目录可由用户自定义（直接丢当前目录也行）。只扫任务目录/指定目录、
   最多 2 层，不碰无关文件。核对"对应步骤、必须包含、预期结果、可读性"，
   不通过就给出具体补拍清单，避免一次读几十张图浪费 token。
8. **绘图交给 writer**：流程图、架构图、时序图、SWOT 图等报告插图不列入用户截图清单，
   只列在「writer 需要绘制的图」里；用户提供依据，writer 负责画。
9. **先盘点再问**：先看用户已经给了什么，再列缺口；缺材料说明影响，用户说没有就按没有规划。
10. **冲突先协商**：评分表要求但模板没有对应位置（如参考文献/摘要）时先问，
    默认不保留（模板问题），记录原因并同步 writer/reviewer。
11. **截图只截核心**：代码截改动段、终端截命令+结果、GUI 截目标面板；不要整屏/整个 IDE。

## 输出优先级

| 优先级 | 产出 | 内容 | 长度 |
| --- | --- | --- | --- |
| P0 | 执行卡 | 目标与阶段目标、步骤与目标、达成效果、截什么图、卡住怎么办 | 2~4 页 |
| P0 | 实验指导书 | 目的、原理、环境、完整步骤、证据、报告映射、差异/变更 | 按任务 |
| P1 | 截图速查卡 | 拍什么、必须包含什么、文件名 | 1 页内 |
| P2 | 报告映射 | 每节写什么、用哪些证据 | 半页~1 页 |
| P3 | 细节 | 任务形态、目的矩阵、差异、变更应对 | 放在指导书 |

超过长度预算时，先砍背景和理论，**不要砍步骤和截图**。

## 安装

把整个 `report-planner/` 目录复制到对应平台的 skills 目录。以 Claude Code 为例：

```text
~/.claude/skills/report-planner/
```

## 使用

直接把材料目录或文件发给 Agent，并说明你的诉求，例如：

> 这是我们这周的网络实验指导书和报告模板，老师口头说实验室没有三层交换机，
> 让我们用路由器做单臂路由。帮我规划一下实验步骤，标出每一步要截什么图。

> 这是电子商务概论的实验要求和模板，没说要截图，但我不知道调查类实验该留什么材料，
> 帮我做一份现场能照着做的执行卡。

Agent 会：

1. 盘点材料（可用 `scripts/scan_materials.py`）；
2. 确认真实方案与指导书差异；
3. 判定任务形态；
4. 拆步骤、定成功判据、给失败分支；
5. 把截图提示写进每一步；
6. 映射报告章节；
7. 输出 `实验执行卡.md`（步骤/预期结果速查 + 截图速查 + 照做清单 + 报告映射）
   和 `实验指导书.md`（目的、原理、环境、完整步骤、证据、报告映射、差异）。
   **两份都产出**；开工前先问代码/实践部分怎么处理（代写/骨架/你写我审）、
   交付格式、Word/WPS、模板能否改、公式是否可编辑。
8. 你做完一个阶段后，把截图放进 `Pictures/` 或直接上传，它会核对截图是否对应步骤和
   预期结果，不通过时告诉你补拍什么、预期画面是什么；**验收后不会直接跳 writer**，
   而是先给“继续下一阶段 / 修改执行卡 / 补证据”三个选项。

## 材料扫描脚本

```bash
# 扫描整个目录，输出 Markdown 清单
python scripts/scan_materials.py . --out 材料清单.md

# 同时输出 JSON，控制每个文件的提取长度
python scripts/scan_materials.py . --out 材料清单.md --json 材料清单.json --max-chars 12000
```

支持 `.docx` / `.pptx` / `.xlsx` / `.pdf`（需 pypdf）/ 文本文件；
旧版 `.doc` / `.ppt` / `.xls` 会提示先转换。脚本只读，不执行宏、不打开外链、不解压压缩包。

可选依赖：

```bash
pip install python-docx python-pptx openpyxl pypdf
```

```

├── references/
│   ├── intake.md              # 材料盘点、追问话术、用户描述优先
│   ├── task-types.md          # 八种任务形态与步骤骨架
│   ├── evidence-planning.md   # 证据反推、截图规范、防返工
│   ├── execution-card-template.md  # 默认产出：执行卡/截图速查/照做清单
│   ├── screenshot-review.md   # 分阶段截图验收：检查清单/判定/补拍话术
│   ├── plan-template.md       # 实验指导书模板（必做）
│   ├── handoff.md             # 交接给 writer/reviewer
│   └── examples.md            # 跨学科示例
└── scripts/
    └── scan_materials.py      # 材料盘点与正文提取
```

## 边界

**做**：任务解码、步骤拆解、证据规划、截图清单、报告映射、执行卡、变更应对。

**不做**：替用户操作实验环境、编造数据/截图/访谈/文献、代写报告正文、
替用户决定老师没有说明的要求、绕过学术诚信规范。
