# 证据规划

> 执行卡里，截图/证据提示必须**内联到每一步**，并在执行卡前面放一张「截图速查卡」；
> 本文是背后的详细方法，供展开细节或写详细版时使用。

## 1. 核心思路：证据链，不是截图清单

报告里的每一个结论，都应该能回答：**凭什么？** 证据规划就是把"结论"和"材料"连起来：

```
报告结论 ← 分析/判断 ← 数据/现象 ← 采集动作 ← 步骤
```

规划时从结论倒推：

1. 这一节要下什么结论？（例如"配置生效，连通性恢复"）
2. 这个结论需要看到什么？（接口状态、ping 结果、前后对比）
3. 这些东西在哪一步产生？（配置后、重启后）
4. 怎么保证事后能复核？（版本、参数、时间、原始数据）

**只规划"要采什么"，不预设"结果是什么"。**

---

## 2. 证据类型

| 类型 | 能证明什么 | 采集要点 | 常见问题 |
| --- | --- | --- | --- |
| 截图 | 界面状态、配置、输出、网页数据 | 完整窗口、版本/路径/时间可见、关键区域标注 | 只截局部、看不清、无版本、压缩过度 |
| 数据表 | 测量、问卷、财务、实验记录 | 表头、单位、样本量、原始与处理后分开 | 只有汇总、无单位、改过原始值 |
| 日志/输出 | 程序运行、系统事件、命令结果 | 时间戳、命令、返回码、错误信息 | 只截最后一行、无上下文 |
| 代码 | 实现逻辑、关键算法 | 文件名、函数名、关键片段、运行结果 | 只贴代码、无运行证明、与报告不一致 |
| 照片 | 装置、现场、实物、参观 | 原始照片、时间地点、关键细节 | 网图、模糊、涉及他人隐私 |
| 问卷/访谈 | 调研过程与原始观点 | 题目、样本量、渠道、匿名转写 | 诱导性问题、样本过小、无同意 |
| 引用/文献 | 理论、数据、案例来源 | 作者、年份、标题、页码/URL、访问日期 | 无出处、百科当权威、格式混乱 |
| 版本/过程记录 | 项目过程、个人贡献 | 提交记录、会议纪要、分工表、里程碑 | 事后补编、无法对应到人 |
| 计算过程 | 数据处理、财务测算 | 公式、代入值、中间结果、工具 | 只给结果、无法复核 |

## 3. 证据分层：L1 / L2 / L3

| 层级 | 定义 | 判断标准 | 执行策略 |
| --- | --- | --- | --- |
| **L1 必采** | 缺了报告写不成，或核心评分项无法证明 | 没有它，某一节只能写空话 | 写进执行卡；没拿到不进入下一步 |
| **L2 建议采** | 让分析更具体、更有说服力 | 有它，分析能从"是什么"到"为什么" | 时间允许就采 |
| **L3 保险采** | 成本极低、可能用不上 | 多拍一张全景/细节、多存一份原始数据 | 关键步骤顺手做 |

### 为什么 L3 能防返工

截图需求变化通常来自三种情况：

1. 老师后来说"要看到版本号/完整窗口"——如果当初只拍了局部，只能重做；
2. 报告要写对比分析——如果当初只拍了成功结果，没有失败/前后对比，只能重做；
3. 实际方案临时改变——如果旧证据仍然能证明同一结论，就不必重做。

L3 的做法：

- **每个关键步骤多拍一张"全景"**：窗口、菜单、版本、路径、时间都在画面里；
- **多存一份原始材料**：原始数据、日志、配置文件、未剪裁照片；
- **记录失败现场**：报错、异常现象、回退过程，往往比成功截图更有分析价值；
- **保留过程版本**：中间文件、旧版配置、测试记录，不要只留最终版。

## 4. 没有明确截图提示时，怎么反推

### 4.1 决策顺序

```
指导书/任务书明写的要求
        ↓ 没有
模板章节暗示的内容
        ↓ 没有
评分表里的动词与权重
        ↓ 没有
任务形态的通用证据清单
        ↓ 仍不确定
"什么能说服老师" + 问用户/老师
```

### 4.2 四条反推原则

| 原则 | 问法 | 证据例子 |
| --- | --- | --- |
| 证明我做了 | 怎么证明这一步确实执行了？ | 操作界面、现场照片、提交记录、签到 |
| 证明我做对了 | 怎么证明结果是正确的？ | 验证输出、测试通过、验收签字、复测 |
| 证明结果可复核 | 别人凭什么相信这个结果？ | 版本、参数、原始数据、时间地点、样本量 |
| 证明分析有依据 | 分析里的每个判断靠什么支撑？ | 前后对比、对照组、图表、引用、异常记录 |

### 4.3 按报告章节反推

把模板章节逐节问："这一节要写什么？写这个需要看到什么？"

| 报告章节 | 通常需要的证据 |
| --- | --- |
| 实验目的/背景 | 指导书、课程目标（通常不需要学生截图） |
| 实验环境 | 设备型号、软件版本、拓扑/装置图 |
| 实验步骤 | 关键操作界面、命令、参数、过程记录 |
| 实验结果 | 成功/失败现象、输出、数据表、图表 |
| 结果分析 | 前后对比、对照、异常解释、计算过程 |
| 问题与解决 | 报错截图、排查过程、修复前后 |
| 总结/心得 | 不需要新证据；引用前面的事实 |
| 参考文献 | 文献条目、引用位置 |

### 4.4 按评分表反推

评分表里的动词就是证据需求：

| 评分描述里的词 | 需要什么证据 |
| --- | --- |
| "详细描述/完整" | 过程证据要覆盖关键步骤，不能跳步 |
| "对比/比较" | 至少两组条件的数据/截图，最好有表格 |
| "分析/解释" | 原始数据 + 判断依据 + 可能原因 |
| "验证/证明" | 独立验证结果，不只是配置页 |
| "规范/排版" | 图表编号、单位、引用格式、文件命名 |
| "创新/改进" | 基线版本 + 改进版本 + 效果对比 |

## 5. 截图规范

### 5.1 一张合格截图必须包含

- **身份**：设备名/主机名/用户名（可脱敏）、项目名、文件名；
- **版本**：软件版本、系统版本、工具版本；
- **位置**：路径、菜单层级、页面 URL；
- **时间**：系统时间/日志时间（如与结论相关）；
- **内容**：本步骤的关键参数、状态、输出；
- **上下文**：命令 + 输出、配置 + 状态、图表 + 坐标轴/图例。

### 5.1.5 只截核心

- **代码**：只截改动段/关键函数/报错行，带文件名和行号；完整代码用文本块，不截图。
- **终端**：只截命令 + 关键输出 + 提示符，不要整屏历史和无关窗口。
- **GUI**：只截目标对话框/面板/关键字段；只有拓扑/装置全景才截大图。
- **桌面**：不要截整个桌面/整个 IDE；截图后按核心区域裁剪，保留能证明应用/版本的标题栏。
- 一图一结论；无关区域裁掉，别让评审在整屏里找关键字段。

### 5.2 拍摄时机

| 时机 | 拍什么 | 为什么 |
| --- | --- | --- |
| 操作前 | 初始状态、基线数据、环境版本 | 事后无法还原 |
| 操作中 | 关键配置、参数、中间结果 | 证明过程，便于排错 |
| 操作后 | 最终状态、验证输出 | 证明结果 |
| 异常时 | 报错、异常现象、日志 | 分析问题与解决过程 |
| 收尾时 | 保存后的状态、导出结果、备份 | 证明可复现/已保存 |

### 5.3 标注与脱敏

- 用**细框、箭头、编号**标关键区域；不要把文字盖在数据上。
- 一张图只表达一个主要结论；多个结论分图或加编号。
- 打码：姓名、学号、手机号、身份证、他人账号、内部 IP、密钥、住址。
- 保留原始文件；标注后的图另存，不要覆盖原图。
- 文件名建议：`S<步骤号>_<内容>_<日期>.png`，例如 `S3_接口状态_20261019.png`。

### 5.4 不同场景的截图重点

| 场景 | 必含元素 | 补充 |
| --- | --- | --- |
| 命令行/终端 | 命令、完整输出、提示符/路径、返回码 | 失败时保留报错上下文 |
| 网络设备 | 设备名、接口、IP、状态、版本 | 配置页 + 验证命令输出 |
| IDE/代码 | 文件名、关键代码、运行/测试结果 | 目录结构、依赖版本 |
| 网页/平台 | URL、页面标题、日期、关键数据 | 数据来源页、筛选条件 |
| 数据工具 | 数据表头、字段、筛选条件、图表坐标轴 | 原始数据与处理后数据 |
| 问卷后台 | 问卷标题、回收量、时间、样本分布 | 题目页、原始数据导出 |
| 现场/装置 | 全景 + 细节、时间地点、设备标识 | 照片原图、避免他人隐私 |

---

### 5.5 绘图/示意图：交给 writer，不算用户证据

指导书/模板要求画流程图、架构图、时序图、SWOT 图、示意图等时：

- **不要**把它放进用户的截图清单，也不要要求用户先画好再拍照；
- 用户只需要留下**支撑图的原始证据**：报文顺序、packet number、拓扑截图、数据表、引用原文；
- 图本身由 `report-writer` 在报告里绘制；
- 在规划/交接里单列「writer 需要绘制的图」：

  | 图 | 画什么 | 依据的证据 |
  | --- | --- | --- |
  | 图 13 | 基础通信流程 | E8、E10 的报文顺序 |
  | 图 18 | 进阶握手与数据流 | E15、E19-E21 |

**例外**：如果图本身就是任务产物（设计草图、原型、手绘稿、CAD 图），它属于任务产出，
用户仍可能要完成；但它不是"截图"，报告插图仍由 writer 负责。

## 6. 非截图证据规范

### 6.1 数据表

- 必须有表头、单位、样本量/行数、采集时间；
- 原始数据与处理后数据分开存放；
- 不要只保留平均值，保留每个样本；
- 异常值标注原因，不要直接删除。

### 6.2 日志/输出

- 保留时间戳、命令、返回码、错误信息；
- 不要只截最后一行成功提示；
- 长日志保存为文本文件，报告里引用关键片段。

### 6.3 代码

- 报告里放关键片段，完整代码作为附件/仓库；
- 片段要能看出文件名、函数名、输入输出；
- 代码里的参数与报告描述一致；
- 不贴无法解释的网上代码。

### 6.4 问卷/访谈

- 问卷：题目、选项、样本量、渠道、时间、无效问卷处理；
- 访谈：时间、方式、对象匿名标识、提纲、转写、关键原话；
- 涉及他人：知情同意、匿名化、不公开可识别信息；
- 不诱导、不篡改、不虚构回答。

### 6.5 引用/文献

- 记录作者、年份、标题、来源、页码/URL、访问日期；
- 正文引用与文末列表一一对应；
- 直接引用加引号并标页码；
- 网络资料注明访问日期，优先权威来源。

### 6.6 过程/项目记录

- 分工表写清"谁负责什么、产出是什么、工作量占比"；
- 会议纪要含时间、参与人、决策、待办；
- 版本记录含提交人、时间、变更内容；
- 个人贡献要能对应到具体文件/模块/章节。

## 7. 防返工：变更场景与应对

| 如果发生 | 旧证据是否有效 | 需要补什么 | 不要做什么 |
| --- | --- | --- | --- |
| 老师要求补版本号/完整窗口 | 局部截图部分有效 | 重拍关键步骤的全景图 | 不要重做整个实验 |
| 方案从 A 改成 B | 环境/基线/部分结果可能仍有效 | 补 B 的关键配置与验证 | 不要删掉 A 的记录（可作为对比） |
| 设备不够，换替代设备 | 目的相同则旧数据可能可复用 | 补替代设备的型号、配置、验证 | 不要把替代设备写成原设备 |
| 老师口头加要求 | 已有证据可能仍支撑 | 按新要求补 1~2 项证据 | 不要静默忽略新要求 |
| 数据/样本不足 | 已有样本仍有效 | 说明样本限制，补采集过程记录 | 不要编造样本量 |
| 报告字数/章节调整 | 证据不变 | 调整章节映射 | 不要为了凑字数编内容 |

**原则：先判断旧证据是否仍能支撑同一结论；能支撑就不重做，只补缺口。**

## 8. 隐私、伦理与学术规范

- **最小必要**：只采集完成任务必需的证据，不收集无关个人信息。
- **打码/匿名**：截图、访谈、照片中的他人信息要脱敏；用编号代替姓名。
- **知情同意**：访谈、录音、拍照前说明用途；课程要求时取得书面/口头同意。
- **保密**：涉密单位、内部系统、未公开数据，按课程/单位规定处理；不确定就问老师。
- **不造假**：不编数据、不 P 图、不用网图冒充现场、不伪造签名/验收记录。
- **不抄袭**：引用要标注；成品报告只参考格式，不抄内容；代码/文案注明来源。
- **可追溯**：保留原始文件与采集时间，便于老师核查。

## 9. 证据清单自检

- [ ] 每个 L1 证据都能对应一个报告结论/评分项
- [ ] 每个证据都写清了"拍什么/记什么、必须包含什么、什么时候采、文件名"
- [ ] 关键步骤有全景 + 细节，或至少有一张信息完整的图
- [ ] 不可复现的材料（环境、原始数据、报错）已优先采集
- [ ] 失败/异常现场有记录，不只是成功结果
- [ ] 截图/数据/访谈的隐私处理方式已写明
- [ ] 变更时能判断哪些旧证据仍有效，不需要整套重做
- [ ] 没有把流程图/示意图列成用户截图；已列入 writer 要画的图
- [ ] 没有要求用户编造任何数据或证据
